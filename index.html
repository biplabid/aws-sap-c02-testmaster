Start Here

Overview

AWS SAP-C02 TestMaster is a practice platform for the AWS Certified Solutions Architect – Professional exam. It offers three ways to study — quick one-at-a-time questions, a short timed quiz, and a full-length mock exam — plus a statistics dashboard that tracks your progress across attempts.

The app runs entirely in your browser (or as a desktop app on Windows), and no account is required: your progress, answers, and attempt history are saved locally on your device by default. You can optionally sign in with Google to sync your completed results to your own Google Drive so they follow you to another device — see Syncing with Google Drive.

Use the top navigation bar (or the menu button on smaller screens) to switch between modes. The current section is always highlighted.

Random Test

The most flexible way to study. Pick a question set and answer questions one at a time, in random order, with immediate feedback after each submission — correct/incorrect, the right answer, and the explanation.

  • Mark as Done — permanently excludes a question from future Random Test sessions for that set, so you can focus on questions you haven't mastered yet. This flag is remembered even after you close the app.
  • Reset Progress — clears all "done" flags for the currently selected set from the intro screen, if you want to start over.

Random Test has no timer and no scoring — it's meant for low-pressure, question-by-question learning.

Timed Quiz

A focused, 20-question quiz with a 40-minute countdown timer, meant to simulate a short section of the real exam.

  • Navigate freely between questions using Previous / Next or the question palette; your answers are saved automatically as you go.
  • The timer keeps running even if you switch away from the Timed Quiz view or close and reopen the app — it's based on elapsed real time, not just active screen time.
  • If time runs out, the quiz submits automatically with whatever answers you've selected so far.
  • Click Finish Quiz at any point to submit early.

Mock Exam

A full-length, 75-question simulation with a 3-hour timer — the closest thing to sitting the real SAP-C02 exam.

  • Question palette — jump to any question directly; answered questions and questions marked for review are color-coded.
  • Mark for Review — flag a question to revisit later without losing your place.
  • Review Screen — before submitting, see a full breakdown of answered, unanswered, and marked questions, with the remaining time.
  • Submit confirmation — you'll be warned if you have unanswered or marked questions before the exam locks in your answers.

Reading Your Results

Both Timed Quiz and Mock Exam show the same kind of results screen after you submit: your score, how many questions you answered, and a per-question list.

Click the Correct or Incorrect summary tile to filter the question list down to just those questions. In this filtered view, each question expands to show:

  • The answer you selected (or "Not answered").
  • A Show correct answer & explanation button (for incorrect questions) that reveals the correct answer and the full explanation, so you can understand exactly why an answer was right or wrong.

Click the tile again, or the Show all questions button, to return to the full list.

Statistics

The Statistics dashboard aggregates every Timed Quiz and Mock Exam attempt you've completed:

  • Summary cards — total attempts, average score, best score, and total study time.
  • Score by Domain radar chart — shows your accuracy across different SAP-C02 exam domains, so you can see where to focus your remaining study time.
  • Recent Attempts bar chart — your last 10 attempt scores at a glance.
  • Attempt history table — every attempt with its date, type, score, and time used.
ⓘ

The dashboard only appears once you've completed at least one Timed Quiz or Mock Exam attempt.

Question Sets

Every practice mode has a Question Set selector. The app ships with several bundled sets covering different practice questions; any question sets you import via Upload appear in the same dropdown, in every mode.

Uploading Your Own Questions

The Upload page lets you add a new question bank from a specially formatted .docx file. Each question block must be separated by three dashes (---), and the file needs at least 50 questions. See the Upload page itself for the exact structure required.

⚠

Saving an uploaded set requires Chrome or Edge — it relies on the File System Access API to write the new set directly into the app's data folder. Other browsers can't save the file, though all other features work everywhere.

On success, you'll be asked to pick this project's data folder once; the new set is saved as the next available setN.json and immediately shows up as a selectable set everywhere.

Syncing with Google Drive (Optional)

Signing in with Google is entirely optional — everything above works with no account at all. If you'd like your completed attempt history and "Mark as Done" flags to follow you to another device, click Sign in in the top-right corner.

  1. Sign in with Google. This identifies you and, in the same step, asks for permission to create/edit files it needs in your Drive — nothing else in your Drive is touched.
  2. Choose Drive Folder (from the account menu, click your avatar). Pick an existing folder or create a new one in Google's picker — this is where your data file (testmaster-data.json) will live, fully visible in your normal Drive.
  3. From then on, finishing a Timed Quiz or Mock Exam, or marking a question Done, automatically syncs to that folder in the background. The account menu shows a live "Syncing…" / "Synced" status.

Signing in again later — on this device or a new one — and reconnecting the same Drive folder brings your historical results back automatically; nothing is ever silently overwritten, results from every device are merged together.

⚠

On a brand-new device or browser, the app can't automatically rediscover which folder you used before (that's how Google's restricted Drive permission works). Click Reconnect Drive Folder in the account menu and pick the same folder again in the picker — your data is still there, this just re-grants access to it.

What does not sync: an in-progress Timed Quiz or Mock Exam only lives on the device you're taking it on. Only completed results sync.

Your Data & Privacy

TestMaster doesn't have a backend or a database of its own. Everything — your in-progress sessions, saved answers, timer state, "done" flags, attempt history, and theme preference — is stored locally in your browser's LocalStorage. If you never sign in, nothing ever leaves your browser.

This also means your local data is tied to a specific browser profile and device. Clearing your browser's site data for this app (or switching browsers/computers) will reset your progress and statistics — unless you've signed in and connected a Google Drive folder (see above), in which case your completed history can be pulled back down.

If you do sign in, TestMaster only ever requests the narrow "app-created files" Drive permission — it can see and edit the one folder/file you explicitly picked, never your wider Drive. You can revoke access at any time from your Google Account permissions page.

Troubleshooting

My Timed Quiz or Mock Exam didn't save my progress

Make sure your browser allows LocalStorage for this site (private/incognito windows sometimes restrict or clear it) and that you're not clearing site data between sessions.

The Upload button says my browser isn't supported

Uploading requires the File System Access API, currently available only in Chromium-based browsers (Chrome, Edge). Try one of those.

I want to restart a set from scratch

In Random Test, use Reset Progress to clear "done" flags for a set. For Timed Quiz or Mock Exam, use Start New Quiz / Start New Mock Exam on the results screen, or just start the mode again — a fresh, in-progress session always replaces a completed one.

Design Principles

Overview

TestMaster is a vanilla HTML/CSS/JavaScript single-page application — no build step, no bundler, no framework, and no backend. Every js/*.js file attaches a small module to a shared window.TestMaster namespace, and index.html loads them all as plain <script> tags in dependency order.

The same static files run two ways:

  • In a browser — served by any static file server (e.g. python -m http.server), so fetch() can load the bundled question JSON without hitting CORS restrictions.
  • As a Windows desktop app — an Electron shell (electron/main.js) starts a local HTTP server over the project root and loads it into a native window, so the exact same code runs unmodified in both contexts.

There is still no server-side persistence: all state lives in the browser's LocalStorage by default. The app writes outside LocalStorage in exactly two opt-in cases: the Upload feature saving a new question set file via the File System Access API, and — if a user signs in with Google and picks a folder — drive-sync.js syncing completed attempt history to that user's own Google Drive. Neither requires or implies a backend of ours; both talk directly from the browser to the relevant Google/browser API.

App Shell & Routing

index.html contains every view as a sibling <section class="view" data-view="..."> inside one .content container. ui.js owns navigation:

  • Any element with a data-nav attribute (top nav links, sidebar links, home page mode cards) is a navigation trigger.
  • Clicking one pushes a history entry for #<view> and toggles the matching [data-view] section's active class — there's no client-side router library, just hash matching.
  • Activating a view dispatches a testmaster:view-change CustomEvent on window, which feature modules listen for to refresh their set selector or resume an in-progress session.
  • Alt+letter keyboard shortcuts and the dark/light theme toggle (persisted to LocalStorage) are also owned by ui.js.

Module Reference

Application Shell

app.js

Entry point. Builds the shared appState object and calls each module's init*Shell function in order.

ui.js

Hash-based view routing, dark/light theme toggle, keyboard shortcuts, toast notifications.

utils.js

Tiny DOM query helpers (qs/qsa) and number formatting used throughout.

Core / Shared Modules

question-engine.js

Fetches a question set, normalizes any raw JSON shape into the canonical question object, and provides shuffle/random-selection helpers. Falls back to two built-in placeholder questions if a set fails to load or normalizes to zero valid questions.

view-helpers.js

Lists available question sets (bundled + uploaded), resolves a set key to its JSON path, renders a question into the shared answer-form markup, and grades single/multi-select answers.

file-sets.js

Discovers uploaded sets remembered in LocalStorage and writes new setN.json files into data/ via the File System Access API.

storage.js

The only module that touches window.localStorage directly. Provides typed get/set helpers plus higher-level session, timer, answer, and statistics APIs.

timer.js

A persisted, elapsed-time-based countdown timer factory used by both Timed Quiz and Mock Exam, so a timer survives a page reload or an app restart.

exam.js

A minimal shared session-state placeholder (appState.exam); each mode currently keeps its own richer state (appState.quiz, appState.mockExam, appState.random) rather than a unified shape.

Practice Mode Modules

random.js

Random Test: untimed, one question at a time, immediate feedback, and per-question "Mark as Done" tracking keyed by question set.

quiz.js

Timed Quiz: 20 questions, 40-minute timer, question palette, filterable Correct/Incorrect results with per-question answer reveal.

mock.js

Mock Exam: 75 questions, 3-hour timer, mark-for-review, a pre-submission review screen, and the same filterable results view as Timed Quiz.

analytics.js

Statistics dashboard: renders summary cards and two Chart.js visualizations (domain radar, recent-attempts bar) from attempt history.

upload.js

Parses a .docx file (via Mammoth.js) into the canonical question shape and hands it to file-sets.js to persist.

Auth & Sync Modules

config.js

Holds the public Google OAuth Client ID (and optional Picker API key) — safe to commit, unlike a client secret.

auth.js

Google Identity Services sign-in/out, access-token lifecycle, and the testmaster:auth-change event other modules react to.

drive-sync.js

Plain fetch()-based Drive REST calls, the folder picker, and the id-based merge that reconciles local and cloud history.

account-ui.js

The header sign-in control and account popover: renders identity, sync status, and the folder-picker/sign-out actions.

Question Data Pipeline

Every question set on disk (data/set1.json … data/set5.json, plus anything saved via Upload) is a flat JSON array of raw question objects. Loading always goes through the same normalization contract in question-engine.js, regardless of the source file's exact field names:

Raw field (accepted aliases)Canonical field
question / prompt / textprompt
type (anything starting with "multi" → multi-select)type: "single" | "multiple"
options[] (string or {id/letter, text})options[]: {id, text}
answer / answers / correctAnswerscorrectAnswers[] (upper-cased letters)
domain, difficulty, explanationpassed through as-is (defaulted if missing)

Any raw question missing a prompt, options, or a correct answer is dropped during normalization. If an entire set normalizes to zero valid questions (or fails to fetch), question-engine.js silently falls back to two generic built-in questions so the UI never renders a blank state — see Known Limitations for why this matters.

Set selection flows through view-helpers.js: getAvailableQuestionSets() returns the bundled sets plus any uploaded sets from file-sets.js, populateSetSelector() fills each mode's <select>, and resolveQuestionSetSource() turns the chosen key into a data/<key>.json path for question-engine.js to fetch.

Practice Mode State

Timed Quiz and Mock Exam share the same lifecycle shape, each owning its own slice of appState (appState.quiz / appState.mockExam):

  1. Start — build a question set (bundled questions shuffled and sliced to the mode's count), or restore an in-progress session from storage.loadExamSession() if one exists.
  2. In progress — every answer change and navigation saves the current answers and session pointer to LocalStorage immediately, and a persisted timer.js instance keeps counting down based on elapsed wall-clock time.
  3. Finish — triggered manually or by timer expiry; computes the score, records the attempt via storage.recordAttempt(), clears the session, and renders the filterable results view.

Random Test (random.js) is simpler and stateless across reloads: it holds an in-memory shuffled pool for the current visit and persists only the per-question "done" flags, keyed by question set.

LocalStorage Schema

Every key storage.js writes is namespaced under sap-c02-testmaster: and JSON-encoded:

KeyShapePurposeScope
settings{ theme, updatedAt }Theme preferenceShared

attempt_historyArray of attempt recordsBacks the Statistics page (list, charts)Per user

answers:<id>{ [questionId]: string[] }Selected answers for a sessionShared

done_questions:<setKey>Array of question IDsRandom Test "Mark as Done" per setPer user

<id> is the session id ("timed-quiz" or "mock-exam"). storage.clearExamSession() clears the session, answers, review flags, and timer together once an attempt finishes.

Per-user scope means the key is additionally prefixed with the signed-in user's stable Google id (sap-c02-testmaster:<sub>:<key>) via storage.setCurrentUser(), which storage.js itself calls in response to testmaster:auth-change — only the data that's ever synced to Drive is scoped this way, so two people signed into different Google accounts on the same browser never see each other's history or done-flags. Signed-out ("guest") use keeps today's plain shared prefix. Shared keys (in-progress session/timer/answer/review state) are deliberately left un-namespaced: they're excluded from Drive sync entirely (see Google Sign-In & Drive Sync), so scoping them would only reintroduce a real bug found during design review — those modules read from storage synchronously at bootstrap, before Google auth can possibly have resolved (it's always asynchronous), so a signed-in user's very first render would otherwise happen under the wrong prefix. random.js and analytics.js additionally listen for testmaster:user-change to refresh their per-user-scoped displays (done-count, statistics) if sign-in resolves or changes while already on that view.

Upload Pipeline

Custom question banks flow through three modules in sequence:

  1. upload.js reads the selected .docx as an array buffer, extracts raw text with Mammoth.js, splits it into ----delimited blocks (minimum 50), and parses each block's Question / Type / Domain / lettered options / Answer / Explanation lines into the canonical question shape.
  2. file-sets.js requests write access to the project's data folder via window.showDirectoryPicker(), determines the next free setN.json name, and writes the parsed questions to it.
  3. The new file name is remembered in LocalStorage (file_sets_index) so view-helpers.js can list it as a selectable set in every mode on subsequent visits, without needing to re-scan the file system.
⚠

Both the directory picker and the write itself depend on the File System Access API, which only Chromium-based browsers implement — there is no fallback download-a-file path for other browsers.

Google Sign-In & Drive Sync

Sign-in is fully optional and additive: with no sign-in, the app behaves exactly as described everywhere else in this document. Signing in layers identity and, once a folder is chosen, Drive persistence on top — via Google Identity Services' client-side token flow (the old gapi.auth2 library was sunset in 2023). There is no backend, so this is an authorization flow (an access token), not a verified ID-token/JWT identity flow — acceptable specifically because nothing server-side ever makes a trust decision based on identity; the real access boundary is enforced entirely by Google on the bearer token against Drive itself.

Sign-in

auth.js calls google.accounts.oauth2.initTokenClient() requesting openid email profile https://www.googleapis.com/auth/drive.file in one consent step, then calls Google's userinfo endpoint with the resulting token to get { sub, email, name, picture }. It dispatches testmaster:auth-change on every sign-in/out, which storage.js, drive-sync.js, and account-ui.js all listen for independently.

Folder selection & the drive.file scope

The drive.file scope (deliberately chosen over full Drive access, to avoid Google's formal OAuth verification process) means the app can only ever see files/folders it created or that the user explicitly granted via Google's official Picker — it cannot search or list arbitrary pre-existing folders. drive-sync.js's chooseFolder() opens the Picker (folder-select mode, which also lets the user create a new folder inline); the chosen { id, name } is remembered per-user in LocalStorage (drive:folder).

Sync

The synced payload is deliberately narrow: a single testmaster-data.json file in the chosen folder containing attemptHistory and doneQuestions only — in-progress session/timer/answer state never syncs (see the shared-vs-per-user distinction in LocalStorage Schema). statistics isn't synced as its own blob either; it's recomputed from the merged history on every sync, removing a class of reconciliation bugs.

Sync is triggered by storage.js dispatching testmaster:data-changed from exactly two places — recordAttempt() and saveDoneQuestions() — debounced 3 seconds before drive-sync.js pushes, and it's always fire-and-forget: a write to LocalStorage always completes synchronously and successfully first, regardless of network or auth state, so a result is never lost even if the sync that follows it fails.

Because two devices can each add attempts offline before either syncs, merging uses record identity rather than "last write wins" by timestamp (which risks silently discarding a real result): attempt history entries are unioned by their existing unique id, and done-question flags are unioned per set (marking done is monotonic in the UI, so union is always correct, never needs to remove).

Analytics Pipeline

analytics.js reads attempt_history and statistics from storage whenever the Statistics view activates. Per-domain accuracy for the radar chart is computed by re-grading every stored attempt's saved questions/answers against viewHelpers.isAnswerCorrect() and grouping by each question's domain field. Both charts are rendered with Chart.js and re-themed (grid/label colors) on every render based on the current light/dark theme.

Desktop Packaging

electron/main.js is the entire Electron main process: on app.whenReady() it starts a local HTTP server (serve-handler) bound to an OS-assigned port over the project root, then opens a BrowserWindow pointed at http://127.0.0.1:<port>/index.html. Context isolation and Node integration are disabled in the renderer (contextIsolation: true, nodeIntegration: false, sandbox: true) — the desktop app has no elevated capabilities beyond what the same page could do in a regular browser tab.

package.json's build field configures electron-builder to produce two Windows targets from npm run dist:

  • NSIS installer — per-user, no admin rights, with Desktop and Start Menu shortcuts.
  • Portable executable — runs directly with no installation step.

Both bundle index.html, css/, js/, data/, and assets/ as-is (via asar packaging) — there's no separate desktop build artifact to keep in sync with the web version.

Known Limitations

⚠

Mock Exam attempts are missing from domain analytics. mock.js's call to storage.recordAttempt() omits the questions/answers fields that quiz.js includes. analytics.js's domain radar chart re-grades attempts from those fields, so Mock Exam attempts silently contribute nothing to the per-domain breakdown even though they still count toward the summary cards and history table.

⚠

data/set4.json has no usable questions. Every entry in that file has an empty options and answer array. question-engine.js normalizes it down to zero valid questions and silently falls back to the two generic built-in questions, repeated to fill the requested count.

⚠

Upload is Chromium-only, with no fallback (e.g. a plain file download) for Firefox or Safari users who want to import a custom set.

⚠

No refresh token, so sign-in doesn't survive a page reload. Google's client-side token flow never issues a refresh token (those only exist in the server-side auth-code flow, which needs a backend this app doesn't have). The access token lives in memory only; auth.js attempts a silent requestAccessToken({ prompt: '' }) renewal on load, which depends on an active Google session and third-party cookies — expect it to fail outright in Safari (ITP) and intermittently elsewhere, falling back to the visible "Sign in" button. No data is lost either way; only the signed-in session itself needs re-establishing.

⚠

A lost Drive folder reference needs a manual reconnect. The drive.file scope can't rediscover an existing folder by searching — only chooseFolder()'s Picker call has that visibility. If drive:folder is missing (new device, cleared LocalStorage) or stale (folder deleted/unshared, detected as a 404 on the folder's own metadata), drive-sync.js surfaces a "reconnect" status rather than silently syncing nothing; the user re-picks the same folder and the app regains access to it and its existing contents.

⚠

Google Sign-In does not work in the packaged Electron desktop app. Google blocks OAuth inside embedded/webview browsers by design (an anti-phishing measure), and Electron's BrowserWindow is exactly that. This was an explicit, confirmed non-goal for this feature — the desktop build keeps working local-only, exactly as before.

⚠

No automated test suite. There's no unit, integration, or end-to-end test tooling configured in package.json; correctness currently relies on manual verification.

Extending the App

Adding a new practice mode

Create a new js/<mode>.js module following the existing pattern (an IIFE attaching to window.TestMaster.<mode>, an init<Mode>Shell(appState) entry point), add its markup as a new [data-view] section in index.html, register it in app.js's bootstrap sequence, and add matching [data-nav] links in the header and sidebar.

Adding a new question set

Either drop a new data/setN.json file (array of raw questions matching the schema in Question Data Pipeline) and add it to the BUILT_IN_SETS list in view-helpers.js, or let a user add one at runtime through the Upload page.
